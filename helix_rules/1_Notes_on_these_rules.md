📌 Key Takeaway: Clarifying the TTPs

Before tuning detections, it helps to separate the three distinct techniques that often get conflated during an incident:

Concept	What It Actually Is	How TA Helix / UNC6671 Uses It
Rogue MFA Registration (T1556.006)	Enrolling a new authentication factor (OATH TOTP app, FIDO2/passkey, or phone number) on the victim's identity profile via mysignins.microsoft.com/security-info.	Primary Persistence: After vishing the user onto a spoofed AiTM portal (e.g., *passkey*.com, *mfa*.com) and capturing the session cookie, the actor replays the token and immediately adds their own OATH MFA device for persistent access.
Rogue Device Registration (T1098.005)	Joining or registering a virtual machine/workstation into Entra ID (Azure AD Joined / Registered) to obtain a Primary Refresh Token (PRT) and satisfy "Compliant/Registered Device" policies.	Secondary / Conditional: Less common in pure UNC6671/Helix SaaS smash-and-grabs (which rarely touch endpoints), unless they need to bypass device-based Conditional Access or pivot further.
Device Code Phishing (T1528)	Tricking a user on a call into visiting microsoft.com/devicelogin and entering an 8-character alphanumeric code generated by the attacker's OAuth client.	Alternative Vishing Lure: Instead of hosting an AiTM proxy domain, some vishing operators read out a device code over the phone. However, Helix/UNC6671 heavily favors manually gated AiTM panels with passkey/SSO lures over standard device code flows.

🔍 Attack Chain Breakdown: Controls & High-Signal Detections

Standalone rules for "MFA registered" or "SharePoint file downloaded" are notoriously noisy in large tenants. To cut through the noise, correlate contextual signals across the five phases of the Helix/UNC6671 kill chain:

1. Initial Access: Help Desk Vishing & AiTM Token Capture (T1566.004, T1557)

How it happens: Actors pull employee contact details (e.g., via RocketReach), spoof internal corporate or IT help desk phone numbers, and call employees (often on personal mobile devices) claiming an urgent "passkey" or "MFA upgrade" is required. They direct the user to a live, operator-gated AiTM domain (e.g., addssopasskey[.]com, mfaregister[.]com, <org>.myaccountoptions[.]com).
Preventive Controls:
  Enforce Phishing-Resistant MFA: Require FIDO2/WebAuthn security keys or device-bound passkeys (e.g., Windows Hello for Business, Okta FastPass), which cryptographically bind authentication to the legitimate domain and neutralize AiTM reverse proxies.
  Disable Device Code Flow: Block the Device Code authentication flow via Conditional Access for all standard users if it isn't strictly required.
  Establish a Verified IT Callback Protocol: Train employees that IT will never cold-call to walk them through MFA/passkey enrollment on external domains, and implement an internal verification mechanism.
High-Signal Detections:
  Newly Registered / Lookalike Lure Domains: Alert on DNS queries or proxy/CASB traffic matching regex patterns for authentication lures (*passkey*, *sso*, *mfaregister*, *myaccountoptions*).
  AiTM Token Replay Telemetry: Correlate a successful interactive login with an immediate session replay from a different IP/ASN (specifically residential proxies like NodeMaven, Luminati, DataImpulse, SOAX, or hosting providers like PrivateLayer AS51582) within minutes of the initial auth.

2. Persistence: Rogue MFA Enrollment (T1556.006)

How it happens: Using the hijacked session token from a residential proxy (often geo-matched to the victim's city/ISP), the attacker accesses My Sign-Ins / My Profile, registers an attacker-controlled OATH TOTP token or passkey, and occasionally triggers Self-Service Password Reset (SSPR).
Preventive Controls:
  Lock Down MFA & SSPR Registration via Conditional Access: Require Trusted Network Locations (corporate VPN/SASE egress IPs) AND Compliant/Hybrid-Joined Devices to access the Register security info user action. This single control stops attackers from registering a rogue MFA from a residential proxy, even if they steal a valid session token.
  Time-Bound Help Desk MFA Resets: Eliminate standing MFA admin privileges; use PAM/Identity Governance (or temporary AD group membership) for short-window MFA resets.
High-Signal Detections (Fixing the Noisy Rule):
  Instead of alerting on every User registered security info event, correlate MFA registration with:
    1. Preceding Auth Anomalies: MFA registration immediately preceded by multiple MFA failures, abandoned push notifications, or a sign-in from a non-corporate/residential proxy ASN.
    2. Session/Device Mismatch: User registered security info where the session comes from an unmanaged device (isCompliant == false and isManaged == false) or where the IP/User-Agent shifts mid-session.
    3. Secondary Factor Addition: Alert specifically when a user who already has an established MFA method suddenly registers a new Software OATH token or Passkey from a new ASN/IP.

3. Defense Evasion: Hiding the Tracks (T1070.004, T1090)

How it happens: To keep the victim from noticing the new MFA device, UNC6671/Helix operators systematically delete security notification emails and MFA modification alerts (or create inbox rules to hide them).
Preventive Controls:
  Out-of-Band Notifications: Route MFA registration alerts to a secondary channel (e.g., push notification to the existing authenticator app or manager/SOC webhook) in addition to email.
  Shorten Session Lifetimes: Reduce token lifetimes and enforce strict sign-in frequency for sensitive portals (My Sign-ins, Admin Portals, SharePoint).
High-Signal Detections:
  Alert Deletion / Inbox Manipulation Post-MFA Change: Detect HardDelete / SoftDelete or New-InboxRule events in Exchange Unified Audit Logs targeting emails with subjects containing "security info", "MFA", or "authentication method" within 15 minutes of a User registered security info event.

4. Discovery: Cloud & SharePoint Enumeration (T1526)

How it happens: Shortly after access (or ~24 hours later from a separate VPS/proxy IP), the actor enumerates Entra ID directory attributes (Get user flows, Get API connectors, Get identity providers) and maps SharePoint repositories using automated pagination queries.
High-Signal Detections:
  Specific SharePoint Search Signatures: Monitor Microsoft Purview / Unified Audit Logs (SearchQueryPerformed) for the exact reconnaissance queries favored by this cluster:
    contentclass:STS_Site
    contentclass:STS_Web
    Wildcard pagination queries matching indexdocid>{integer}
  Non-Browser User-Agents in SharePoint/Graph: Alert on SharePoint discovery or Entra ID enumeration originating from scripting user agents such as python-httpx/*, python-requests/*, Node clients, or Microsoft.Graph.Client/* tied to standard user accounts.

5. Collection & Exfiltration: Bulk SharePoint & Exchange Theft (T1213, T1530)

How it happens: Actors run automated scripts from dedicated hosting ASNs (e.g., AS51582 - PrivateLayer, AS23470 - ReliableSite, AS399629 - BL Networks, or Mullvad/M247 IPs) to mass-download SharePoint/OneDrive files and harvest Exchange mailboxes before sending an extortion demand ~1 week later.
Preventive Controls:
  Conditional Access App Control (Defender for Cloud Apps / CASB): Block bulk downloads from unmanaged devices or non-corporate IP ranges, and enforce session-level restrictions that prevent token replay from external ASNs.
High-Signal Detections:
  Velocity + ASN/User-Agent Correlation: Rather than a flat threshold on FileDownloaded / FileAccessed (which fires whenever someone syncs OneDrive), trigger when:
    High-volume FileDownloaded or FileAccessed events occur across multiple distinct SharePoint sites within a short window, AND
    The session originates from a non-standard User-Agent (python-requests, python-httpx, WindowsPowerShell/5.1), a hosting/VPN ASN, or a user who registered a new MFA method within the last 72 hours.
  Anomalous MailItemsAccessed: Watch for high-volume Exchange MailItemsAccessed activity, especially associated with suspicious ClientAppId/API ID pairs (such as ClientAppId: 9199bf20-a13f-4107-85dc-02114787ef48).

⚠️ Common Pitfalls to Watch Out For

Built-in Telemetry & Policy Lag: Entra ID Conditional Access group changes and Unified Audit Log ingestion (especially SharePoint FileDownloaded and SearchQueryPerformed) can lag by 10 to 30+ minutes. Automated scripts can exfiltrate gigabytes of SharePoint docs before a SIEM threshold rule fires, making preventive Conditional Access on MFA registration and unmanaged device downloads critical.
Same-Geo Residential Proxies: Because Helix uses residential proxies (like NodeMaven) matched to the victim's city and ISP (e.g., Comcast, AT&T), traditional "Impossible Travel" or "Foreign Country Sign-in" rules will completely miss the initial token replay. Focus on Device Trust state (isManaged/isCompliant), User-Agent shifts, and SearchQueryPerformed anomalies instead.
